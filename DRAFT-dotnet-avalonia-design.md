# DRAFT — .NET / Avalonia desktop stack standard

> **Status: design decisions answered by the owner; implementation not
> started.** Nothing in here is implemented or a standard yet. Per
> `CLAUDE.md` ("New tech stacks"), no package, workflow, template or skill
> change lands until the owner says to proceed. When it does, this file
> becomes `dotnet-avalonia.md` (minus this banner and the "Decisions"
> section) and the checklist at the bottom is executed in order.
>
> Nothing here has been built or run — it's modelled on the existing
> Wails/Go and Electron patterns in this repo and on VisualAssault's
> generator. Items marked **untested** need a real end-to-end run before
> anyone relies on them.

## Why this exists

The first app that needs it is a cross-platform (Windows + Linux) hardware
power monitor. Avalonia was chosen over Electron for its small footprint
(an always-on tray monitor shouldn't idle at 150+ MB) and because the
sensor layer (LibreHardwareMonitorLib, NVML, RAPL) is .NET-native. None of
the five standards categories — theming, release/CI, update-check, SQLite
location, licensing — currently cover a .NET stack.

**Scope: Windows (`win-x64`) and Linux (`linux-x64`).** macOS is
deliberately out of scope (same as the app's own sensor layer). The design
doesn't prevent adding `osx-arm64` later; it just doesn't build it.

## Summary of the design

| Category | Proposal | Shape it follows |
|---|---|---|
| Theming | New `packages/avalonia` in **VisualAssault**, generated by `generate_packages.py`; consumers **vendor** a tag-sourced copy via a re-vendor script | Go/static-asset consumers in `themes-versioning.md` |
| Release/CI | New `release-avalonia.yml` + `ci-dotnet.yml`; packaging with **Velopack** (`vpk`): Windows `Setup.exe`, Linux AppImage | `release-electron.yml` (build tool packages and publishes) |
| Update-check | **Velopack** directly, no KVG_Standards package; the standard defines the wiring contract | `electron-updater` |
| SQLite location | New `packages/dotnet/KvgDbLocation` incl. dev/packaged isolation + single-instance lock | `kvg_dblocation` + `db-location-versioning.md` |
| Application menu | No stock menu bar exists; minimal in-window Help/About | `electron-menu.md` (intent, not mechanics) |
| Logo & branding | Same checklist; icons generated from `assets/logo.png` by a checked-in script | `app-standards` "Logo & branding" |
| Licensing | AGPL-3.0 default; add a .NET dependency-license check recipe | `licensing.md` |
| Versions | Pin to current .NET LTS and current Avalonia major, checked at creation | `electron-versioning.md` |

## 1. Theming

**Producer side (VisualAssault repo, separate PR):** add
`packages/avalonia/` and an `emit_avalonia()` to `scripts/generate_packages.py`,
so it is deterministically generated from `themes/THEMES.md` like the other
four. Nothing about a color is defined twice.

Generated output:

- `VisualAssault.Themes.cs` — `VisualAssaultThemes.All` (id → name + 15 token
  colors). Theme ids are `snake_case` (`blue_oval`), matching the Tkinter and
  Flet packages, so a saved theme preference means the same thing across
  stacks.
- `VisualAssault.axaml` — one `ResourceDictionary` per theme exposing every
  token twice: `Va<Token>Color` and `Va<Token>Brush` (e.g. `VaBgBrush`,
  `VaPrimaryActionBrush`, `VaSurfaceBrush`). 15 tokens × 14 themes.
  `primaryActionText: null` is emitted as the theme's `text` value (that is
  what the token reference defines `null` to mean), so `DynamicResource`
  always resolves.
- `VisualAssault.Fluent.axaml` — maps tokens onto Avalonia's Fluent theme
  resource keys (window/control backgrounds, foreground, accent, borders,
  hover/pressed states) so **stock controls** (buttons, text boxes, list
  items, scroll bars) pick the theme up with no per-control styling.
- `ThemeManager.cs` — `Apply(string id)` swaps the merged dictionary at
  runtime (themes are switchable live, like the picker in the other stacks)
  and sets `RequestedThemeVariant` to Dark/Light from the background's
  relative luminance, so any control the Fluent mapping misses still gets
  legible defaults.
- Version: bump VisualAssault to **`v0.3.0`** (additive package → minor,
  per its own HOW_IT_WORKS rule). All packages share one version.

**Consumer side:** one theme dependency per repo, pinned to a tag — same
rule as everywhere. Avalonia has no git-subdirectory dependency mechanism and
VisualAssault deliberately isn't published to a registry, so consumers use
the **vendoring pattern already written up for Go/static consumers**:

- The generated files live in `src/<App>/Themes/VisualAssault/`, each with a
  header comment: source tag, "do not hand-edit".
- `scripts/update-visual-assault-avalonia.sh <tag>` re-fetches them from that
  VisualAssault tag (the reviewable equivalent of bumping a version string).
- **Violation to flag:** theme files with no tag header, hand-edited theme
  files, a hand-rolled palette, or a pin to `main`.

**Open/untested:** how deep the Fluent key mapping goes. Proposal: start with
the ~20 keys that cover window, text, buttons, inputs, lists, scrollbars and
tabs; expand when an app hits an unthemed control, in VisualAssault, not
locally.

## 2. Release / CI

New reusable workflow **`.github/workflows/release-avalonia.yml`**, called by
the same `templates/auto-release.yml` + `templates/cut-release.yml` pair as
every other desktop app (both triggers, `VERSION_BUMP.md`, as usual). It
follows `release-electron.yml`'s model: the stack's own packaging tool
(Velopack's `vpk`, like `electron-builder`) makes the installer and
publishes the update feed. The shared Inno `windows-installer` action is
**not** used here.

Inputs: `version`, `app_name` (used as Velopack's `--packId`),
`project_path` (the `.csproj` to publish), `main_exe`, `icon_path`,
`dotnet_version`, `run_tests` (default `true`).

Per OS (matrix `windows-latest` → `win-x64`, `ubuntu-latest` → `linux-x64`):

1. `dotnet test` (skippable) — gives apps an M4-qualifying test run in the
   release path too.
2. `dotnet publish -c Release -r <rid> --self-contained -o publish
   -p:Version=<tag-without-v>`. **Trimming off** (Avalonia/XAML bindings
   and reflection make it fragile; revisit only with a real size problem).
3. Pull the previous release's packages so deltas can be built
   (`vpk download github …`), then
   `vpk pack --packId <app_name> --packVersion <semver> --packDir publish
   --mainExe <main_exe> --icon <icon_path> --outputDir out`.
4. Publish `out/` (installer, full + delta packages, update feed files) to
   the GitHub Release for the tag, with the usual "## Installing" body:
   Windows → run `…Setup.exe`; Linux → download the `.AppImage`,
   `chmod +x`, run. Unsigned-build warning stays; no macOS line.

Output per platform, as understood from Velopack's docs: Windows gets a
`Setup.exe` plus update packages; **Linux gets only an AppImage — Velopack
does not make a Linux installer.** The version must be valid SemVer
(`v1.2.3` → `1.2.3`), which the tags from `auto-release.yml` already are.

**Version stamping is built in.** `release-go-gui.yml` shipped without it
and every build reported "update available" forever (see the 2026-09-04
entry in `REPO_SCOPE.md`). Here `-p:Version` and `--packVersion` are always
set from the tag; the app reads its version from Velopack
(`UpdateManager.CurrentVersion`), never from its own constant.

**Also:** `ci-dotnet.yml` (restore, build `-warnaserror`, optional
`dotnet test`) mirroring `ci-go.yml`, for PRs; `templates/*.yml` TODO
comment lists get the new entry.

**To verify against Velopack's current docs / a real run before this is
written** (the docs site wasn't reachable when this was drafted): the exact
upload command for GitHub Releases, how per-OS channels/feeds avoid
colliding when two runners publish to one release, and the Windows install
location (understood to be per-user, no admin prompt). **Untested**
end-to-end until a first real release.

## 3. Update-check — Velopack, used directly

Same position as Electron: a real, maintained library (MIT) already solves
this, so **no KVG_Standards package**. The standard defines the wiring so
apps don't invent variants; the first app (the power monitor) becomes the
reference implementation, as Sweeper's `main.ts` is for Electron.

- `VelopackApp.Build().Run()` is the first statement in `Main` (handles
  install/uninstall/update hooks).
- An `UpdateManager` pointed at the app's own GitHub repo; a silent check on
  startup plus a "Check for updates" button in the in-window Help/About
  (§5); download, then apply and restart.
- The running version comes from Velopack. When the app is not an installed
  build (a dev run) the update check is skipped, not an error.
- Updates apply only to installed builds: the Windows `Setup.exe` install
  and, on Linux, the AppImage. There is no tar.gz, so there is no
  non-updating Linux variant to explain.
- **Violation to flag:** a hand-rolled updater, or an Avalonia app with a
  release pipeline and no update check.

Because this replaces the earlier plan (a C# port of `packages/go/kvgupdate`),
there is no `KvgUpdate` package and no Windows self-replace code to own or
test; that risk moves to Velopack. Still to verify: that the update source
works for a public GitHub repo with no token, and the exact .NET
`UpdateManager` source API.

## 4. SQLite database location — `packages/dotnet/KvgDbLocation`

Same default / effective / set (copy-on-relocate) / reset shape as Sweeper's
`dbLocation.ts` and `kvg_dblocation`, plus the three "instance isolation"
requirements from `db-location-versioning.md`, translated:

1. **Dev and packaged never share a data folder.** Default dir is
   `<LocalApplicationData>/<app>` (maps to `~/.local/share/<app>` on Linux);
   a Debug / non-published run uses `<app>-dev`. The package exposes
   `PinDataDirectory(appName)`; call it first thing in `Program.Main`.
2. **Single instance** via an exclusive lock file in the data dir
   (`FileShare.None`) — cross-platform, released automatically on crash.
   Named mutexes behave differently on Unix, so they aren't used. A second
   launch exits (optionally signalling the first to focus; app's choice).
   The Electron `appInitialized` race doesn't exist in this form, but the
   rule stands: a second launch must never open a window or the DB before
   the first has finished initializing.
3. **Never silently create an empty DB when a *configured* path is missing**
   (`GetConfiguredDbPath()` returns the raw override with no fallback; the app
   shows Quit / Use-default).

**Engine:** `Microsoft.Data.Sqlite` (MIT) in **WAL mode** — real incremental
writes, so the `sql.js` whole-file-clobber failure doesn't apply (same
position as RolePlaymate's `node:sqlite`); items 1–3 are still required.

The consumer-owned Settings UI is unchanged: current path **and file size in
KB/MB/GB**, choose existing, choose new (copy), reset, then restart.

**Delivery:** the C# file is copied into the app from a tag with
`scripts/update-kvg-dblocation.sh <tag>`, which stamps the source tag into a
header comment (the Godot `kvg_update` precedent). Fix bugs here, then
re-run the script; never patch the vendored copy. **Future work:** publish
it as a NuGet package once someone owns a registry publisher.

## 5. Application menu

Avalonia has no stock File/Edit/Window bar to strip, and `TextBox` ships its
own cut/copy/paste context menu, so the Electron rules (and their
`context-menu` workaround) have nothing to fix. Proposal: **no menu bar**;
instead an in-window Help/About section with repo link, issues link,
version, and "Check for updates". `NativeMenu` is *not* used because Linux
global menus depend on the desktop environment. **Violation to flag:** a
File/Edit/Window-style menu bar with no stated reason; dev-only items
(Avalonia DevTools) not gated to Debug builds.

## 6. Logo & branding

Same placement checklist, Avalonia equivalents:

- README hero — unchanged.
- Window/taskbar icon — `Window.Icon` from an `AvaloniaResource`.
- In-app usage — logo next to the app name.
- Packaged icon — `<ApplicationIcon>` (`.ico`) in the `.csproj` (Windows
  exe), and the same icon passed to `vpk pack --icon` for the installer and
  the Linux AppImage (which needs one).
- Generation — `scripts/generate-icons.py` (Python + Pillow, KVGrainy's
  pattern) emits a multi-size `.ico` and PNGs from `assets/logo.png`; outputs
  are committed. Not ImageSharp (Six Labors' license needs a check before it
  goes anywhere near an AGPL repo).

## 7. Licensing

AGPL-3.0 default, unchanged. Add to `licensing.md` a recipe for .NET:
`dotnet list package --include-transitive`, then check each package's
`<license>` / `licenseUrl` in its `.nuspec` (same "permissive / LGPL /
GPL-or-later fine, anything else needs a look" triage). Expected baseline:
.NET runtime, Avalonia, SkiaSharp, HarfBuzzSharp, Microsoft.Data.Sqlite and
Velopack are MIT. App-specific dependencies (a sensor library, a charting library) are
checked per app, not here.

## 8. Versions

Mirror `electron-versioning.md`: target the **current .NET LTS** and the
**current Avalonia major**, checked against `dotnet --list-sdks` / NuGet at
creation or audit time — never copied from a sibling repo's csproj. Use
version ranges only where NuGet normally does (floating minor/patch is fine;
pin exact in a lock file via `RestorePackagesWithLockFile`). Violation to
flag: more than one major behind, or an app that skipped the check.

## 9. Pinning

KVG_Standards still has no tags, so the same interim exception applies
(`@main` in the workflow `uses:` and vendoring from `main`) until the first
tag; moving to it is the follow-up already described in
`update-check-versioning.md`.

## Decisions (answered by the owner)

1. **Updater: Velopack, used directly.** Chosen over porting `kvgupdate`
   (Go) to C#: it is a maintained library like `electron-updater`, and it
   removes the unproven Windows self-replace code from this repo. Cost: a
   second release/packaging path next to the Inno one used by the Python,
   Go and Flet stacks (Electron already differs the same way).
2. **Shared code delivery: copy the files into each app from a tag**, via a
   re-vendor script. With Velopack this now applies to `KvgDbLocation`
   only. **Future work:** publish it as a NuGet package once someone is
   ready to own a registry publisher (and decide how apps authenticate to
   GitHub Packages, or use nuget.org instead). Until then, vendoring is the
   standard.
3. **Linux artifact: AppImage (Velopack's only Linux output).** This
   replaces the earlier "tar.gz only" answer, which assumed the in-repo
   updater; with Velopack there is no tar.gz.
4. **Theme: lives in VisualAssault.** There is no Avalonia package there
   yet (it has CSS, Tkinter, Flet, Angular), so it is created there, not
   locally in an app. Depth: Fluent key mapping for common controls;
   anything an app finds unthemed is fixed in VisualAssault.
5. **Menu: no menu bar; in-window Help/About.**
6. **Left to the app's own design (not the standard):** the power monitor
   needs elevation to read CPU sensors. An elevated helper installs
   per-machine, which conflicts with a per-user, no-admin install and
   update. Likely answer: UI per-user + helper updated through its own
   installer step.

**Still needed from the owner:** a go-ahead to start implementing (step 1
below). Step 1 also needs push access to VisualAssault, which this session
doesn't have yet.
